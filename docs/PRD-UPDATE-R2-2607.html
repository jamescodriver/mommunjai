Problem Statement

ระบบที่เพิ่ง ship (มีบุตรยาก = เลือกฝ่ายชาย/หญิงอย่างเดียว) หยาบเกินไปเทียบกับปัญหาจริงของลูกค้ากลุ่มนี้ — สาเหตุต่างกันมาก (PCOS, รังไข่เสื่อม, ฮอร์โมนต่ำ, ผนังมดลูกบาง, ปัญหาฝ่ายชาย, น้ำหนักเกิน) และแต่ละสาเหตุต้องการสินค้าคนละชุด การถามแค่เพศไม่ช่วยให้คำแนะนำตรงจุด ในอีกด้านหนึ่ง ธุรกิจต้องการให้ LINE OA เป็นช่องทางปิดการขาย ไม่ใช่ให้เว็บให้ข้อมูลจนจบแล้วลูกค้าไม่มีเหตุผลต้องคุยต่อ

Goals

  • คำแนะนำ personalize ลึกขึ้น 2 ชั้น: category + ปัญหาเฉพาะ (เฉพาะกลุ่มมีบุตรยาก)
  • เว็บทำหน้าที่ lead-gen ไม่ใช่จบเซอร์วิส — เพิ่มอัตราคนกดไปคุยต่อใน LINE
  • ลดการกรอกซ้ำ + เก็บ consent ตั้งแต่ต้นทาง
  • เครื่องมือนับวันไข่ตกอ่านง่ายขึ้น ระดับแอปมาตรฐาน
  • ปลดบล็อก mapping สินค้าที่ทีมเคยขอ confirm (PDF-14)

Non-Goals (รอบนี้ยังไม่ทำ)

  • เครื่องมือออกกำลังกาย (PDF-15) — ยังไม่มีสูตร/ผู้เชี่ยวชาญ sign-off
  • แบบทดสอบความเครียด (PDF-16) — ยังไม่มี scale ที่มีสิทธิ์ใช้งานถูกต้อง
  • จองตรวจแล็บ/ผูก GFC เชิง commerce (PDF-18 ส่วนที่เหลือ) — รอ partnership
  • LIFF เต็มรูป — ยังใช้กลไก resume-token ผ่านปุ่ม Rich Menu เดิม
  • แสดงตัวเลข BMI ตรงๆ — client เห็นด้วยเองว่า "ทำให้งง"
  • ส่วนสูง/อายุตัวเลขเป็น field บังคับทุกหน้า — เก็บเฉพาะจุดที่ใช้จริง

User Stories

ผู้หญิงเตรียมตั้งครรภ์ (ธรรมชาติ)

  • อยากตอบคำถามน้อย ได้คำแนะนำทั่วไปทันที ไม่ต้องเจอแบบสอบถามยาวเหมือนคนมีปัญหาเฉพาะ

ผู้หญิงมีบุตรยาก

  • อยากติ๊กปัญหาที่ตรงกับตัวเอง เพื่อได้สินค้าตรงปัญหาจริง
  • อยากบอกว่าอยู่ขั้นการรักษาไหน เพื่อได้แผนที่ไม่ขัดกับสิ่งที่หมอสั่ง

ฝ่ายชาย

  • อยากมีทางเข้าชัดเจนทั้งใน "เตรียมตั้งครรภ์" และ "มีบุตรยาก" ไม่ใช่ category แยกที่รู้สึกโดดเดี่ยว

ลูกค้าทั่วไป — หลังกรอกเสร็จ

  • อยากเห็นคำแนะนำเบื้องต้นทันที เพื่อรู้สึกว่ากรอกมีค่า จนอยากคุยต่อใน LINE
  • กลับมาทำใหม่ อยากให้จำข้อมูลเดิม แก้ได้โดยไม่กรอกซ้ำ

ทีมงาน (staff ฝั่ง LINE OA)

  • อยากเห็นว่าลูกค้าติ๊กปัญหาอะไร + อยู่ขั้นการรักษาไหน เพื่อให้คำปรึกษาแผนเต็มตรงจุดโดยไม่ถามซ้ำ

Requirements — P0 (Must-have)

P0 R1 — ปรับโครงสร้าง Category เป็น 4 หมวดจริง
  • เตรียมตั้งครรภ์ / ตั้งครรภ์แล้ว / ให้นมบุตร → เข้าแบบสอบถามตรงๆ ไม่มีหน้าจอเลือกปัญหาเพิ่ม (พฤติกรรมเดิมไม่เปลี่ยน)
  • "เตรียมตั้งครรภ์" ต้องมีทางเลือก ฝ่ายชายอยู่ภายในหมวดนี้ ไม่ใช่การ์ดแยกระดับบนสุด (stage=male เดิมผูกกับ "มีบุตรยาก" อย่างเดียว — รอบนี้ต้อง reachable จาก "เตรียมตั้งครรภ์" ด้วย)

Acceptance

  • กดเข้า 3 หมวด → ข้าม stage-picker ตรงเข้า step "name" ทันที
  • การ์ด "เตรียมตั้งครรภ์" มีทางเลือกย่อย "ฝ่ายชาย" แยกจากเส้นทางหลัก

แทนที่การ์ด "ฝ่ายหญิง/ฝ่ายชาย" ด้วย checkbox 7 ข้อ (เลือกได้หลายข้อ ยกเว้น "ไม่แน่ใจ" ที่ exclusive):

P0 R3 — อายุ/ส่วนสูงเป็น context ชั้น 2 ไม่ใช่ field บังคับ
  • อายุ: ใช้ age_range เดิมเป็น modifier เชิงคุณภาพ (35+ → "ควรได้โปรตีนช่วงบนของเกณฑ์") — ยังไม่ล็อกเป็นสูตรตัวเลขจนกว่า confirm (Open Q #4)
  • ส่วนสูง: ไม่เพิ่มเป็น field ทั่วไป — ถามเฉพาะเมื่อติ๊ก "น้ำหนักเกิน" ใน R2 แล้วคำนวณ BMI ภายใน แสดงผลเป็นคำอธิบายเชิงคุณภาพ ไม่โชว์ตัวเลข

Acceptance

  • ไม่ติ๊ก "น้ำหนักเกิน" → ไม่เจอคำถามส่วนสูงเลย
  • ติ๊ก "น้ำหนักเกิน" → เจอคำถามส่วนสูงเพิ่ม 1 ข้อ ได้คำแนะนำเจาะจงระดับ
  • ไม่มีตัวเลข "BMI: 27.3" ปรากฏที่ไหนเลย
P0 R4 — เปลี่ยนคำถาม ART เป็น "เข้าสู่กระบวนการทางการแพทย์ไหม?"

ค่าใหม่ 5 ตัวเลือก: ยัง / IUI / IVF-ICSI (เด็กหลอดแก้ว) / บำรุงไข่ / เตรียมผนังมดลูก

⚠️ client เว้น "-" ลอยว่างหลัง "เตรียมผนังมดลูก" — อาจตั้งใจใส่ตัวเลือกที่ 6 (Open Q #1) — ทำ 5 ตัวเลือกตามข้อความจริงไปก่อน

Breaking schema change: artPlan เดิม (none/iui/ivf/icsi) → ค่าใหม่ 5 ค่า กระทบ lib/calc/vitamins.ts, lib/report.ts, app/plan/page.tsx, app/api/lead/route.ts, app/api/customer/resume/route.ts, lib/tagging.ts, tests — ต้องมี migration mapping สำหรับ lead เก่า (none→ยัง, iui→IUI, ivf/icsi→IVF-ICSI)

Acceptance

  • ปุ่มเลือก 5 ตัวเลือกใหม่แสดงถูกต้อง
  • lead เก่าที่มีค่า artPlan แบบเดิมยังอ่าน/แสดงผลได้ไม่ error
P0 R5 — Depth-tiering: teaser ทั่วไป vs แผน 90 วันเต็ม
  • กลุ่ม "ยัง" + "ไม่แน่ใจ" → คำแนะนำวิตามินทั่วไป ไม่ใช่แผน 90 วันเต็ม
  • กลุ่ม "เตรียมผนังมดลูก" → แผนบำรุงเต็ม + ราคา
  • 🟡 ข้อเสนอ (Open Q #3): กลุ่ม IUI/บำรุงไข่ → ระดับกลาง (แผนย่อ ไม่โชว์ราคาเต็ม)

Acceptance

  • "ยัง"+ไม่ติ๊กปัญหา → เห็นการ์ดสั้น ไม่มี 8-ส่วนของ 90-day report
  • "เตรียมผนังมดลูก" → เห็นแผนเต็ม+ราคา (เหมือนวันนี้)
P0 R6 — Gate แผนเต็มไว้หลังส่ง ticket เข้า LINE OA
  • หลัง /api/lead สำเร็จ → โชว์สรุปสั้น (pillar อ่อนสุด 1-2 ข้อ + สินค้า 2-3 ตัว ไม่มีราคา/dosage เต็ม) + ปุ่ม "รับแผนบำรุง 90 วันฉบับเต็ม ผ่าน LINE OA" พร้อม ticket
  • แผนเต็ม (reports+/r/[code]) ยัง generate+เก็บเหมือนเดิม — แค่ไม่ auto-render ทันที ต้องผ่าน LINE
  • /r/[code] เดิมยังเปิดตรงได้ไม่ต้อง login (กัน backward-compat ลิงก์ที่แชร์ไปแล้ว)

Effort ต่ำ — โครง ticket+webhook+resume-token (PDF-05/06) มีครบแล้ว แค่เปลี่ยนจุด "เปิดเผยลิงก์"

Acceptance

  • submit /plan → ไม่เห็น ReportView เต็มทันที เห็นแค่ teaser+ticket+ปุ่มไป LINE
  • พิมพ์ ticket ใน LINE OA → ยังได้ Flex พร้อมลิงก์ /r/[code] เต็มเหมือนเดิม
  • /r/[code] ยังเปิดตรงได้ไม่ต้อง auth
P0 R7 — ย้าย consent มาอยู่ต้นทาง flow
  • ย้ายจาก step "contact" (ท้ายสุด) → step "intro" (แรกสุด) ทั้ง /plan และทุก tool เดี่ยว
  • เหตุผล: วันนี้คำตอบก่อนถึง "contact" ยังไม่ผ่าน consent เลย — ย้ายต้นทางให้ถูกต้อง PDPA ตั้งแต่ต้น
  • ต่อยอด PDF-06: consent+LINE ID ผ่านเร็วขึ้น → ผูก customer_id เร็วขึ้น แม้ทำแค่ tool เดี่ยว

Acceptance

  • เข้า /plan หรือ /tools/* ครั้งแรก เจอ consent gate ก่อนเห็นคำถามใดๆ
  • ปฏิเสธ consent → ใช้เครื่องมือได้ปกติแบบ anonymous — ไม่บังคับ consent ถึงจะใช้แอปได้
P0 R8 — Identity key: ยึด LINE ID เป็นหลัก เบอร์โทรเป็น secondary

🎯 คำแนะนำจาก PM: ใช้ LINE user ID เป็น key หลักต่อไป (ตามที่ dev แล้วใน PDF-06) ไม่เปลี่ยนไปใช้เบอร์โทรเป็น key หลัก เพราะ:

  • เบอร์โทรเปลี่ยนมือได้บ่อยในไทย ไม่มี OTP verify → เสี่ยง merge ข้อมูลผิดคน
  • LINE ID มาจาก webhook ที่ verify signature แล้ว ส่วนเบอร์โทรกรอกเองพิมพ์ผิดได้
  • โครงที่มีอยู่แล้ว (resume-token, menuFlex) ผูกกับ LINE ID ทั้งหมด — เปลี่ยนตอนนี้ = rewrite ของที่เพิ่งเสร็จ

เบอร์โทรใช้เป็น secondary/soft-match เท่านั้น — โชว์ให้ staff เห็นเป็น hint ไม่ auto-merge

Acceptance

  • customers.line_user_id ยังเป็น unique key หลัก ไม่เพิ่ม constraint บนเบอร์โทร
  • หน้า staff แสดงเบอร์โทรตรงกันเป็น hint "อาจเป็นคนเดิม?" ไม่ auto-link
P0 R9 — Ovulation tool redesign: วันไข่ตกใหญ่สุด ตัวหนังสือน้อย
  • วันไข่ตกเป็น hero element ตัวใหญ่สุด (แทนที่ "ช่วงมีโอกาสสูง" ที่เด่นสุดตอนนี้)
  • ตัด intro/disclaimer ให้สั้นลง (ย้าย disclaimer เต็มไปไว้ใน collapsed/tooltip)
  • สูตร 14-day luteal phase ไม่ต้องแก้ (client ยืนยันถูกแล้ว) — ปิด PDF-09 บางส่วน

Acceptance

  • วันไข่ตกใช้ font-size ใหญ่กว่าทุก element อื่นในผลลัพธ์
  • จำนวนคำในหน้าก่อนกดคำนวณลดลงอย่างมีนัย

Success Metrics

เนื่องจากเป็น client project ภายใน วัดแบบเบาๆ พอให้เห็นทิศทาง:

  • Leading: % ผู้กรอก /plan จบแล้วกดไป LINE OA (ก่อน/หลัง R6) · % ที่ติ๊กปัญหาใน checkbox ใหม่ (R2)
  • Lagging: อัตราปิด ticket เป็นลูกค้าจริงใน LINE OA (ต้องให้ทีม LINE OA รายงานเอง)
  • วิธีวัด: query จาก events/tag_assignments ที่มีอยู่แล้ว + staff รายงานรายเดือน
