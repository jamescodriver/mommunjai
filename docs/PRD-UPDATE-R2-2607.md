## Problem Statement

ระบบที่เพิ่ง ship (มีบุตรยาก = เลือกฝ่ายชาย/หญิงอย่างเดียว) หยาบเกินไปเทียบกับปัญหาจริงของลูกค้ากลุ่มนี้ — คนที่มีบุตรยากมีสาเหตุต่างกันมาก (PCOS, รังไข่เสื่อม, ฮอร์โมนต่ำ, ผนังมดลูกบาง, ปัญหาฝ่ายชาย, น้ำหนักเกิน) และแต่ละสาเหตุต้องการสินค้าคนละชุด การถามแค่เพศไม่ช่วยให้คำแนะนำตรงจุด ลูกค้าจึงอาจรู้สึกว่าได้คำตอบทั่วไปเกินไปและไม่กลับมาซื้อ ในอีกด้านหนึ่ง ธุรกิจต้องการให้ LINE OA (ที่มีทีมให้คำปรึกษาจริง) เป็นช่องทางปิดการขาย ไม่ใช่ให้เว็บให้ข้อมูลจนจบแล้วลูกค้าไม่มีเหตุผลต้องคุยต่อ

## Goals

1. คำแนะนำ personalize ลึกขึ้น 2 ชั้น: **category** (สถานะ/อายุครรภ์) + **ปัญหาเฉพาะ** (เฉพาะกลุ่มมีบุตรยาก) → สินค้าที่แนะนำตรงปัญหาจริงมากขึ้น
2. เว็บทำหน้าที่ lead-gen ไม่ใช่จบเซอร์วิส — ให้ teaser พอรู้สึกว่าได้ประโยชน์ แต่แผนเต็มต้องผ่าน LINE OA → เพิ่มอัตราคนกดไปคุยต่อใน LINE
3. ลดการกรอกซ้ำ + เก็บ consent ตั้งแต่ต้นทาง → ผู้ใช้กลับมาแก้ไขได้โดยไม่ต้องกรอกใหม่ทั้งหมด (ต่อยอดระบบจดจำลูกค้าที่ทำไปแล้ว)
4. เครื่องมือนับวันไข่ตกอ่านง่ายขึ้น ระดับเดียวกับแอปมาตรฐานที่ผู้ใช้คุ้นเคย
5. ปลดบล็อก mapping สินค้าที่ทีมเคยขอ "confirm" ไว้ (PDF-14) ให้เป็นของจริงที่ dev ต่อได้ทันที

## Non-Goals (รอบนี้ยังไม่ทำ)

- **เครื่องมือออกกำลังกาย** (PDF-15) — ยังไม่มีสูตร/ผู้เชี่ยวชาญ sign-off ตามที่ค้างไว้เดิม ทำตอนนี้เสี่ยงแนะนำผิดสำหรับกลุ่มตั้งครรภ์
- **แบบทดสอบความเครียด** (PDF-16) — ยังไม่มี scale ที่มีสิทธิ์ใช้งานถูกต้อง (เช่น PSS)
- **จองตรวจแล็บ/ผูก GFC เชิง commerce** (PDF-18 ส่วนที่เหลือ) — รอ partnership; รอบนี้ทำได้แค่ส่วนความรู้ (R10)
- **LIFF เต็มรูป** — ยังใช้กลไก resume-token ผ่านปุ่ม Rich Menu ข้อความเดิม (ตามที่ตัดสินใจไว้ใน PDF-05/06)
- **แสดงตัวเลข BMI ตรง ๆ ให้ผู้ใช้เห็น** — ตามที่ client เห็นด้วยเองว่า "ทำให้งง" ใช้ภายในเป็นตัวช่วยแนะนำเท่านั้น
- **ส่วนสูง/อายุตัวเลขเป็น field บังคับทุกหน้า** — เก็บเฉพาะจุดที่ใช้จริง ไม่เพิ่มขั้นตอนให้ทุกคนโดยไม่จำเป็น

## User Stories

**ผู้หญิงเตรียมตั้งครรภ์ (ธรรมชาติ ไม่มีปัญหาเฉพาะ)**
- ในฐานะผู้ใช้กลุ่มเตรียมตั้งครรภ์ธรรมชาติ ฉันอยากตอบคำถามน้อยและได้คำแนะนำวิตามินทั่วไปทันที ไม่ต้องเจอแบบสอบถามยาวเหมือนคนมีปัญหาเฉพาะ เพื่อไม่รู้สึกว่าเรื่องเยอะเกินจำเป็น

**ผู้หญิงมีบุตรยาก (มีปัญหาเฉพาะอย่างน้อย 1 อย่าง)**
- ในฐานะผู้ใช้กลุ่มมีบุตรยาก ฉันอยากติ๊กปัญหาที่ตรงกับตัวเอง เพื่อได้สินค้าที่ตรงปัญหาจริง ไม่ใช่คำแนะนำกว้าง ๆ
- ในฐานะผู้ใช้ที่อยู่ระหว่างการรักษาทางการแพทย์ ฉันอยากบอกว่าอยู่ขั้นไหน เพื่อได้แผนที่สอดคล้องกับสิ่งที่หมอแนะนำอยู่แล้ว

**ฝ่ายชาย**
- ในฐานะฝ่ายชายที่มาพร้อมคู่ ฉันอยากมีทางเข้าที่ชัดเจนทั้งใน "เตรียมตั้งครรภ์" และ "มีบุตรยาก" ไม่ใช่ category แยกที่ทำให้รู้สึกโดดเดี่ยวจากคู่

**ลูกค้าทั่วไป — หลังกรอกเสร็จ**
- ในฐานะผู้กรอกแบบสอบถาม ฉันอยากเห็นคำแนะนำเบื้องต้นทันทีหลังกรอกเสร็จ เพื่อรู้สึกว่าการกรอกมีค่า และอยากรู้เพิ่มจนกดไปคุยต่อใน LINE
- ในฐานะผู้ใช้ที่กลับมาทำแบบสอบถามใหม่ ฉันอยากให้ระบบจำข้อมูลเดิม เพื่อไม่ต้องกรอกซ้ำทั้งหมด แต่แก้ไขจุดที่เปลี่ยนได้

**ทีมงาน (staff ฝั่ง LINE OA)**
- ในฐานะทีมที่รับ ticket ต่อใน LINE OA ฉันอยากเห็นว่าลูกค้าติ๊กปัญหาอะไรมาบ้าง + อยู่ขั้นการรักษาไหน เพื่อให้คำปรึกษาแผนเต็มได้ตรงจุดโดยไม่ต้องถามซ้ำ

## Requirements

### P0 — Must-have

#### R1. ปรับโครงสร้าง Category เป็น 4 หมวดจริง — ไม่มี sub-cat ยกเว้น "มีบุตรยาก"
- เตรียมตั้งครรภ์ / ตั้งครรภ์แล้ว / ให้นมบุตร → เข้าแบบสอบถามตรง ๆ ไม่มีหน้าจอเลือกปัญหาเพิ่ม (พฤติกรรมเดิมของ 3 หมวดนี้ไม่เปลี่ยน)
- "เตรียมตั้งครรภ์" ต้องมีทางเลือก **ฝ่ายชาย อยู่ภายในหมวดนี้** ไม่ใช่การ์ดแยกระดับบนสุด (`stage=male` เดิมผูกกับ "มีบุตรยาก" อย่างเดียว — รอบนี้ต้อง reachable จาก "เตรียมตั้งครรภ์" ด้วย)
- **Acceptance:**
  - [ ] กดเข้า 3 หมวด (เตรียมตั้งครรภ์/ตั้งครรภ์แล้ว/ให้นมบุตร) → ข้าม stage-picker ตรงเข้า step "name" ทันที (เหมือนพฤติกรรม `?stage=` ที่มีอยู่แล้ว)
  - [ ] การ์ด "เตรียมตั้งครรภ์" มีทางเลือกย่อย "ฝ่ายชาย" ให้กดแยกจากเส้นทางหลัก

#### R2. เปลี่ยน "มีบุตรยาก" จาก gender-split → checkbox ปัญหาหลายข้อ (multi-select)
แทนที่การ์ด "ฝ่ายหญิง/ฝ่ายชาย" 2 ปุ่มเดิม ด้วย checkbox 7 ข้อ (เลือกได้มากกว่า 1 ข้อ ยกเว้น "ไม่แน่ใจ" ที่ exclusive — เลือกแล้วล้าง selection อื่นอัตโนมัติ):

| Issue | สินค้า (ชื่อทางการ) | หมายเหตุ |
|---|---|---|
| PCOS | **PCO-VIT** | ✅ มีอยู่แล้วใน `lib/calc/vitamins.ts` — ปัจจุบันผูกกับ field `hasPcos` เดี่ยว เปลี่ยนมาผูกกับ checkbox นี้แทน |
| รังไข่เสื่อมก่อนวัย | **Varginaree** | client พิมพ์ "Varginary" — สะกดคลาดเคลื่อน ใช้ชื่อทางการจาก `product-catalog-master.md` #16 ⚠️ Safety Matrix เดิม: ห้ามช่วงใส่ตัวอ่อน/ตั้งครรภ์/ให้นม — คงกฎนี้ไว้ |
| Hormone เพศต่ำ | **Ferti 9 Oil** | ✅ มีอยู่แล้ว (`PRODUCTS.ferti9oil`) |
| ผนังมดลูกบาง | **Ferty (โปรตีน) + Colla Telo** | client พิมพ์ "Collatello" — สะกดคลาดเคลื่อนจาก "Colla Telo" (#1 ใน master catalog) |
| ปัญหาจากฝ่ายชาย | **M-Z All + Motila1** | ⚠️ บล็อกบางส่วน — ดู Open Question #2 |
| น้ำหนักเกิน | **Ferty + สัดส่วน Nutrient** | ใช้ weight+height คำนวณ BMI ภายใน (ดู R3) ไม่โชว์ตัวเลขให้ผู้ใช้เห็น |
| ไม่แน่ใจ | Route ปกติ (ไม่มี targeted product เพิ่ม) | เทียบเท่า flow เดิมก่อนมี checkbox |

- Schema ใหม่: `infertilityIssues: string[]` — **ไม่แทนที่** `stage` (ยังคงเป็น `"infertility"` เหมือนเดิม) แค่เพิ่มมิติย่อย
- **Acceptance:**
  - [ ] เลือก 2+ ปัญหาพร้อมกัน (เช่น PCOS + น้ำหนักเกิน) → รวมสินค้าจากทุกปัญหาที่เลือก ไม่ซ้ำกัน
  - [ ] เลือก "ไม่แน่ใจ" → ล้าง selection อื่นทั้งหมด กลับไปใช้ logic เดิม
  - [ ] Motila1 ไม่ปรากฏในผลลัพธ์จนกว่าจะได้ dosage ยืนยัน (M-Z All แนะนำได้ตามปกติในเวอร์ชัน compliance-safe ที่มีอยู่แล้ว)

#### R3. เพิ่ม "อายุ" และ "ส่วนสูง" เป็น context ชั้น 2 — ไม่ใช่ field บังคับทุกหน้า
- **อายุ**: ใช้ `age_range` ที่เก็บอยู่แล้วเป็น modifier เชิงคุณภาพเข้าโปรตีน/คำแนะนำอื่น (เช่น 35+ → ข้อความ "ควรได้โปรตีนช่วงบนของเกณฑ์") — ⚠️ ยังไม่ล็อกเป็นสูตรตัวเลขจนกว่าจะ confirm (Open Question #4 — ต่อยอด PDF-10 เดิม)
- **ส่วนสูง**: **ไม่เพิ่มเป็น field ทั่วไปใน `/plan`** — ถามเฉพาะเมื่อผู้ใช้ติ๊ก "น้ำหนักเกิน" ใน R2 เท่านั้น แล้วคำนวณ BMI ภายในเพื่อเลือกระดับคำแนะนำ (ปกติ/เกิน/เกินมาก) แสดงผลเป็นคำอธิบายเชิงคุณภาพ **ไม่แสดงตัวเลข BMI**
- **Acceptance:**
  - [ ] ผู้ใช้ที่ไม่ติ๊ก "น้ำหนักเกิน" ไม่เจอคำถามส่วนสูงเลย
  - [ ] ผู้ใช้ที่ติ๊ก "น้ำหนักเกิน" เจอคำถามส่วนสูงเพิ่ม 1 ข้อ แล้วได้คำแนะนำ Ferty+สัดส่วนแบบเจาะจงระดับ
  - [ ] ไม่มีตัวเลข "BMI: 27.3" ปรากฏในหน้าเว็บที่ไหนเลย

#### R4. เปลี่ยน "วางแผนทำเด็กหลอดแก้วไหม" → "เข้าสู่กระบวนการทางการแพทย์ไหม?"
- ค่าใหม่ 5 ตัวเลือก: **ยัง / IUI / IVF-ICSI (เด็กหลอดแก้ว) / บำรุงไข่ / เตรียมผนังมดลูก**
- ⚠️ client เว้น "-" ลอยว่างหลัง "เตรียมผนังมดลูก" ในคอมเมนต์ — อาจตั้งใจใส่ตัวเลือกที่ 6 (ดู Open Question #1) — ทำ 5 ตัวเลือกตามข้อความจริงไปก่อน
- **Breaking schema change**: `artPlan` เดิม (`"none"|"iui"|"ivf"|"icsi"`) → ค่าใหม่ 5 ค่า กระทบ: `lib/calc/vitamins.ts` (`VitaminProfile.artPlan`), `lib/report.ts`, `app/plan/page.tsx` (step "art"), `app/api/lead/route.ts`, `app/api/customer/resume/route.ts`, `lib/tagging.ts`, tests ที่เกี่ยวข้อง
- ต้องมี migration mapping สำหรับ lead เก่า: `none→ยัง`, `iui→IUI`, `ivf`/`icsi`→`IVF-ICSI` (รวมเป็นค่าเดียว)
- **Acceptance:**
  - [ ] ปุ่มเลือก 5 ตัวเลือกใหม่แสดงถูกต้องใน step "art"
  - [ ] lead เก่าที่มีค่า artPlan แบบเดิมยังอ่าน/แสดงผลได้โดยไม่ error

#### R5. Depth-tiering ของแผน: teaser ทั่วไป vs แผน 90 วันเต็ม
- กลุ่ม **"ยัง" + "ไม่แน่ใจ"** (ไม่ติ๊กปัญหาใน R2) → คำแนะนำวิตามินทั่วไป ไม่ใช่แผน 90 วันเต็มรูป
- กลุ่ม **"เตรียมผนังมดลูก"** → แผนบำรุงเต็ม + ราคา
- 🟡 **ข้อเสนอ (รอ confirm — Open Question #3)**: กลุ่ม IUI/บำรุงไข่ → ระดับกลาง (แผนบำรุงย่อ ไม่โชว์ราคาเต็มชุด) เพราะ client ระบุชัดแค่ 2 ปลายทาง
- **Acceptance:**
  - [ ] เลือก "ยัง" + ไม่ติ๊กปัญหา → เห็นการ์ดวิตามินสั้น ไม่มี 8-ส่วนของ 90-day report
  - [ ] เลือก "เตรียมผนังมดลูก" → เห็นแผนเต็ม + ราคา (เหมือนพฤติกรรมวันนี้)

#### R6. Gate "แผนเต็ม" ไว้หลังส่ง ticket เข้า LINE OA — หน้าเว็บให้แค่ teaser
- เปลี่ยนจากพฤติกรรมปัจจุบัน (`ReportView` render เต็มทันทีหลัง submit) เป็น:
  - หลัง `/api/lead` สำเร็จ → เว็บโชว์ **สรุปสั้น** (pillar อ่อนที่สุด 1-2 ข้อ + สินค้าแนะนำ 2-3 ตัว ไม่มีราคา/dosage เต็ม) + ปุ่มเด่น "รับแผนบำรุง 90 วันฉบับเต็ม ผ่าน LINE OA" พร้อมเลข ticket
  - แผนเต็ม (`reports` + `/r/[code]`) **ยัง generate + เก็บเหมือนเดิมทุกอย่าง** (ไม่แตะ backend logic) — แค่ไม่ auto-render ทันที ต้องผ่าน LINE (พิมพ์ ticket code หรือกดปุ่ม "แผนของฉัน" ที่มีอยู่แล้วจาก PDF-05)
  - `/r/[code]` เดิมยังเปิดตรงได้โดยไม่ต้อง login เหมือนเดิม (ไม่ทำ hard-auth-wall เพิ่ม กัน backward-compat ของลิงก์ที่แชร์ไปแล้ว)
- Effort ต่ำ เพราะโครง ticket + LINE webhook + resume-token (PDF-05/06) มีอยู่แล้วครบ — แค่เปลี่ยนจุด "เปิดเผยลิงก์"
- **Acceptance:**
  - [ ] submit `/plan` แล้วไม่เห็น `ReportView` เต็มในหน้าเดียวกันอีกต่อไป เห็นแค่ teaser + ticket + ปุ่มไป LINE
  - [ ] พิมพ์ ticket ใน LINE OA (flow เดิม) ยังได้ Flex message พร้อมลิงก์ `/r/[code]` เต็มเหมือนเดิม
  - [ ] `/r/[code]` ยังเปิดตรงได้ไม่ต้อง auth

#### R7. ย้าย consent มาอยู่ต้นทาง flow
- ย้าย consent checkbox จาก step "contact" (ท้ายสุด) → step "intro" (แรกสุด) ทั้ง `/plan` และทุก tool เดี่ยว (`/tools/*`)
- เหตุผล: วันนี้คำตอบใน stage/health/art ถูกกรอกก่อนผ่าน consent เลย — ย้ายมาต้นทางทำให้ทุก interaction หลังจากนั้นถูกเก็บถูกต้องตาม PDPA ตั้งแต่ต้น
- ต่อยอดระบบจดจำลูกค้า (PDF-06): consent+LINE ID ผ่านตั้งแต่ต้น → ผูก `customer_id` ได้เร็วขึ้น (วันนี้ผูกได้ก็ต่อเมื่อถึงจุด submit) — ผู้ใช้ที่ทำ tool เดี่ยวแล้วไม่ไป `/plan` ต่อ ก็ยังจำได้ถ้ามี LINE ID ตั้งแต่ก่อนเริ่ม
- **Acceptance:**
  - [ ] เข้า `/plan` หรือ `/tools/*` ครั้งแรก เจอ consent gate ก่อนเห็นคำถามใดๆ
  - [ ] ปฏิเสธ consent → ใช้เครื่องมือคำนวณได้ปกติแบบ anonymous (ไม่เก็บ/ไม่จำ) — **ไม่บังคับ consent ถึงจะใช้แอปได้** (คงหลัก client-only-first เดิมตาม `docs/legal-compliance.md`)

#### R8. Identity key: ยึด LINE ID เป็นหลัก — เบอร์โทรเป็น secondary hint
🎯 **คำแนะนำจาก PM** (ตอบคำถามที่ client ถามตรง ๆ ว่า "ควรใช้อะไร"): ใช้ **LINE user ID เป็น key หลักต่อไป** (ตามที่ dev ไปแล้วใน PDF-06 — `customers.line_user_id` unique) **ไม่เปลี่ยนไปใช้เบอร์โทรเป็น key หลัก** เพราะ:
1. เบอร์โทรเปลี่ยนมือ/เปลี่ยนเบอร์ได้บ่อยในไทย และระบบไม่มี OTP verify → เสี่ยง merge ข้อมูลผิดคน
2. LINE ID มาจาก webhook ที่ verify signature แล้ว เชื่อถือได้ว่าเป็นคนกดจริง ส่วนเบอร์โทรที่กรอกเองพิมพ์ผิดได้ไม่มีการยืนยัน
3. โครงที่มีอยู่แล้ว (resume-token, webhook menuFlex) ผูกกับ LINE ID ทั้งหมด — เปลี่ยน key หลักตอนนี้ = rewrite ระบบที่เพิ่งสร้างเสร็จ

เบอร์โทรใช้เป็น **secondary/soft-match** เท่านั้น: เก็บไว้โชว์ให้ staff เห็นในหน้า `/staff` เผื่อกรณี LINE ID ไม่ตรง — **ไม่ auto-merge ข้อมูลจากเบอร์โทรที่ตรงกันโดยอัตโนมัติ** ต้องเป็น manual action ของ staff เท่านั้น (กันข้อมูลข้ามคนโดยไม่ตั้งใจ)

- **Acceptance:**
  - [ ] `customers.line_user_id` ยังเป็น unique key หลัก — ไม่เพิ่ม unique constraint บนเบอร์โทร
  - [ ] หน้า staff แสดงเบอร์โทรที่ตรงกันเป็น hint "อาจเป็นคนเดิม?" เฉย ๆ ไม่ auto-link
